# CFB Pickems — security & correctness audit

**Date:** 21 September 2026  
**Scope:** everything in this repository — iOS app (`Pickems/`, `PickemsWidget/`, `PickemsWatch/`), Firebase backend (`firebase/firestore.rules`, `firebase/storage.rules`, `firebase/functions/`), web admin portal (`firebase/admin/`), public static pages (`web/`), deploy pipeline (`.github/workflows/`, `scripts/`). Firebase project `pickems-fb`, iOS bundle `FannypackInc.Pickems`.  
**Mode:** read-first. No fixes were implemented. Findings were verified against the real `firestore.rules` on the Firestore emulator (see [Appendix A](#appendix-a--emulator-proof-of-concept-results)), against the Cloud Functions source, and against the iOS write paths.

**Verdict:** the backend's only trust boundary is `firestore.rules`, and that boundary has holes that let an ordinary league member (or, in one case, any signed-in stranger) change picks after games are final, forge their season record, and join private leagues without an invite. None of these need a jailbreak or a modified app: they need a Firebase account and a 30-line script, and the repository that documents the rules is public. Cloud Functions are well structured and the admin portal is genuinely claim-gated, but scoring trusts several client-written fields it should not. There is no StoreKit or in-app purchase code in this repository, so the "entitlement" area collapses to "anyone with an account can use the backend for free."

## 2. How to read this document

- **P0** — exploitable today for cheating, unauthorized access, or data integrity loss; or money/availability risk with no mitigation.
- **P1** — likely production bug or a trust-boundary hole that needs an insider (league member/commissioner) or a specific condition.
- **P2** — hardening, compliance, cost, or maintainability that matters for reliability.

Finding IDs: **A** auth, **R** rules, **P** pick/standings logic, **S** purchase, **F** functions/support/admin, **X** cross-cutting. "PoC" refers to the emulator probes in Appendix A. Line numbers refer to the files at commit `6cc80e6`.

## 4. Method and evidence

- Read `firestore.rules`, `storage.rules`, every file in `firebase/functions/src/`, the admin portal auth/callable layer, and the iOS services that write Firestore (`AuthService`, `GroupService`, `PickService`, `ChatService`, `NotificationService`, `AvatarService`, `WeekTransition`, `PicksViewModel`).
- Wrote a throwaway probe script (kept outside the repo, under `/tmp`) that seeds a league on the Firestore emulator and attempts 23 writes/reads as a member, an outsider, and the commissioner against the **unmodified** `firebase/firestore.rules`. Results are in Appendix A. A second probe measured the rules' expression budget for rolling-lock weeks at 5/10/15/20 games.
- Ran the repo's own suites: `firebase/functions` — 91 tests pass; `firebase/tests` (G0 rules) — 39 tests pass. **None of the confirmed holes are covered by an existing test**; the closest one (`blocks a member from rewriting their own seasonWins`) tests `update` only and misses the delete-and-recreate path.
- Checked `git log --all` for key material (none found) and for the personal Gmail address (present in 7 historical commits of the public repo).

## Area 1 — Auth / Sign in with Apple

What is right: the Apple flow uses a fresh `SecRandomCopyBytes` nonce, hashes it with SHA-256 for `ASAuthorizationAppleIDRequest`, and passes the raw nonce to `OAuthProvider.appleCredential` (`Pickems/Core/Services/AuthService.swift` L144–171). Auth state is driven by `addStateDidChangeListener` with an epoch counter so a stale listener cannot clobber a newer session (L64–105). Sign-out clears the FCM token (`AppState.signOut`). Failed email sign-in maps `userNotFound` to the same message as wrong password (no account enumeration in the client). Legal name from Apple is stored only on `users/{uid}`, which only the owner and admins can read. Reauthentication is required before deletion. The admin portal correctly treats the UI as *not* the boundary and re-checks the claim on every token refresh (`firebase/admin/src/auth/AuthContext.tsx`).

### A-1 (P1) No App Check — any client can talk to the backend

**What:** No App Check on Firestore, Functions, or Storage (grep `AppCheck` → only mentions in `docs/WEB_ARCHITECTURE_ASSESSMENT.md`). Email/Password sign-up is enabled and used by the app, so anyone can mint an account from a script using the public web config in `firebase/admin/.env.production`.  
**Who / how:** anyone. Every finding in this document was demonstrated with the Firebase JS SDK and a fake uid; production only differs by needing `createUserWithEmailAndPassword` first.  
**Blast radius:** turns every rules gap from "needs a modified iPhone app" into "needs Node."  
**Fix direction:** enable App Check with App Attest (iOS) and reCAPTCHA Enterprise (admin web); run in *monitor* mode for a release, then enforce on Firestore, Functions, and Storage. This does not fix the rules, it raises the cost of exploiting them.

### A-2 (P2) Account deletion does not revoke the Apple token and leaves authored data

**What:** `AuthService.deleteAccount()` (L771–814) deletes the profile doc, handle, avatar, and the Auth user. There is no call to `Auth.auth().revokeToken(withAuthorizationCode:)`; Apple requires apps using Sign in with Apple to revoke tokens on account deletion (Guideline 5.1.1(v)). `GroupService.leaveAllGroupsForAccountDeletion` removes membership, but pick docs, submissions, nominations, chat messages, and `career/{uid}` keep the uid and `displayName`. `docs/privacy-policy.md` says deletion "removes you from leagues", which is true but incomplete.  
**Fix direction:** capture `authorizationCode` from the reauth credential and call `revokeToken`; add an Auth `onDelete` trigger (v1 `functions.auth.user().onDelete`) that anonymizes `displayName` on picks/messages and deletes `career`, `submissions`, handle, avatar server-side; update the privacy policy.

### A-3 (P2) Account deletion order can leave a half-deleted account

**What:** profile doc, handle reservation, and avatar are removed *before* `user.delete()` (L785–793). If `delete()` throws (network, `requiresRecentLogin` after a slow reauth), the catch signs the user out; the Auth account still exists with no profile, and the username is now free for someone else. Next sign-in silently recreates a profile with a generated name via `ensureUserProfile`.  
**Fix direction:** delete the Auth user first (after reauth), then clean up Firestore/Storage — or do the whole thing in a callable that checks `auth_time` is recent and uses the Admin SDK.

### A-4 (P2) Weak password policy, no email verification

**What:** `validatePassword` requires 6 characters (L413–417), the Firebase minimum. No `sendEmailVerification`, no server-side password policy.  
**Fix direction:** enable Firebase Auth password policy and email-enumeration protection in the console; raise the client minimum to 8+; consider verification before a user can create a league.

### A-5 (P2) No account linking; stale FCM token on session replacement

**What:** Apple and email/password identities are never linked (`link(with:)` is not used). `replaceSessionIfNeeded()` (L836–846) signs the previous user out before email auth but does not call `NotificationService.clearStoredToken`; only `AppState.signOut` does. On a shared device, user A's `users/{A}.fcmToken` still points at the device user B is now using, so A's chat and deadline pushes land on B's screen.  
**Fix direction:** clear the token in `replaceSessionIfNeeded` and in `deleteAccount`; add a link flow or handle `accountExistsWithDifferentCredential` explicitly.

### A-6 (P1) Admin portal: single factor, any admin can mint admins

**What:** `firebase/admin/src/auth/AuthContext.tsx` signs in with email/password or Google popup. No MFA. `setAdminRole` (`firebase/functions/src/admin.ts` L119–156) lets any admin grant the claim to any email; the only guard is "not yourself when revoking." A revoked claim survives in issued tokens up to an hour (documented in `set-admin.mjs`). With the claim, rules grant read/write on every group, week, pick, `users/*` (FCM tokens, legal names), `supportMessages`, and `appConfig/live` (force-update gate).  
**Fix direction:** Google-only admin sign-in with 2-Step Verification enforced on those accounts (or Identity Platform MFA); an env allow-list of admin emails checked in `setAdminRole`; call `revokeRefreshTokens` on revoke; add `frame-ancestors 'none'` for `/admin/**` (X-3).

### A-7 (P2) Debug-only admin and auth-bypass code ships in source

**What:** `DevAdminConfig` (empty gate password, guarded so an empty gate cannot open), `DevAuthBypass.isEnabled = false`, `AdminLoginSheet`, and `signInAsAdmin` (which *creates* a Firebase user if the email does not exist) are all `#if DEBUG`. `AppStoreComplianceTests` exists. This is correct today; the file's own comment says "remove before App Store submission."  
**Fix direction:** delete the dev admin path, or move it behind a build configuration that CI proves is absent from Release; disable the Anonymous provider in the console if unused.

## Area 2 — Firestore security rules + admin custom claims

What is right: the super-admin privilege lives in the ID token, not a document (`isSuperAdmin()`); `adminAudit` is append-only even for admins; `supportMessages` and `adminConfig` are function-only/admin-only; chat `createdAt == request.time` and `reportCount == 0` pins are correct and tested; `inviteCodes` denies `list`; group `list` is membership-scoped; other members' picks are hidden until the week locks. The G0 rules test suite is real and runs in CI.

### R-1 (P0) Anyone who knows a groupId can join any league, no invite code; kicked users can rejoin

**Evidence** (`firebase/firestore.rules`):

```
function isJoiningGroup() {
  return request.resource.data.memberIds.size() == resource.data.memberIds.size() + 1
    && request.auth.uid in request.resource.data.memberIds
    && !(request.auth.uid in resource.data.memberIds)
    && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['memberIds']);
}
…
match /groups/{groupId} {
  allow get: if isSignedIn();
  allow update: if isCommissioner(groupId) || isJoiningGroup() || isLeavingGroup();
  match /members/{memberId} {
    allow create: if isSuperAdmin() || (isSignedIn() && request.auth.uid == memberId);
```

The invite code, `commissionerOnlyInvites`, and "was this user removed" are checked only in Swift (`GroupService.joinGroup`, `PickemGroup.canShareInvite`). PoC **F3-a/b/c**: an outsider added themselves to a private, commissioner-only league, created a member doc, and read another member's locked picks. **F3-d**: a non-member created a member doc in a league they are not in (rules do not require membership for `members` create).  
**Who / how:** any signed-in user who learns a groupId. GroupIds travel in FCM payloads (`data.groupId`), deep links (`?group=`), `publicLeagues/*`, and are known forever to anyone who was ever a member. `groups/{id}` `get` being open to all signed-in users additionally reveals the `inviteCode` and every member uid.  
**Blast radius:** confidentiality of picks (after lock), chat, standings, and roster for every league; harassment via chat; kicked users cannot be kept out.  
**Fix direction:** a `joinGroup` callable (Admin SDK) that validates the code, `commissionerOnlyInvites`, and a `bannedUserIds` array, then writes `memberIds` + member doc atomically. Remove `isJoiningGroup()` from rules; `members` create only via the callable or when `request.auth.uid in group.memberIds`. Change `groups get` to `isGroupMember || isSuperAdmin` and expose invite preview (name, member count) through the callable.

### R-2 (P0) Members can forge their season record by deleting and re-creating their member doc

**Evidence:**

```
match /members/{memberId} {
  allow create: if isSuperAdmin() || (isSignedIn() && request.auth.uid == memberId);
  allow update: if isCommissioner(groupId) || (… self, allow-list of display/notification fields …);
  allow delete: if isCommissioner(groupId) || (isSignedIn() && request.auth.uid == memberId);
```

`create` has no field validation and `delete` is self-allowed. PoC **F2-a** (direct `seasonWins` update) is denied as the existing test expects; **F2-b/c** (delete, then recreate with `seasonWins: 999, role: "commissioner", joinedAt: 1970`) are allowed. Server code then trusts it: `scoreWeek` computes `seasonWins = (member.seasonWins ?? 0) + scored.wins` (`functions/src/index.ts` L656), `refreshLiveStandings` copies `member.seasonWins` into `standings/current` (L562), and `autoCloseSeasons` picks the champion by `seasonWins` then earliest `joinedAt` (L704–713).  
**Blast radius:** leaderboard and dynasty/career records for any league; detectable only by an admin running `adminRescoreWeek`.  
**Fix direction:** rules — `members` create requires `seasonWins == 0 && seasonLosses == 0 && role == 'member' && joinedAt == request.time` and membership in `memberIds`; self-delete only when the uid is already absent from `memberIds` (or via the leave callable). Better: stop storing season totals on a client-creatable doc — derive them in `scoreWeek` by summing scored weeks (the logic already exists in `adminRescoreWeek`).

### R-3 (P0) Members can rewrite the week's lock snapshot and pick after games are final

**Evidence:**

```
function lockSnapshotKeys() {
  return ['pickLockMode', 'weekLockAt', 'gameIds', 'gameKickoffs', 'remainingLockAt'].toSet();
}
function memberWeekFieldUpdate() {
  let changed = request.resource.data.diff(resource.data).affectedKeys()
    .difference(lockSnapshotKeys());
  return changed.hasOnly(['nominationCount']) || …
```

Subtracting the lock keys before `hasOnly()` means a write that touches *only* lock keys produces an empty `changed` set, and an empty set passes `hasOnly`. The repo's own test suite notes the empty-diff behaviour (`firestore.rules.test.js` L526) but only for `status`. Every pick-lock predicate (`pickDeadlineOpen`, `isRollingWeek`, `weekFullyLocked`, `rollingChangedUnlocked`) reads exactly these fields.  
PoC **F1-a**: with `allowLatePicks=false` and a passed deadline, a pick edit is correctly denied. **F1-b**: the same member sets `pickLockMode: "rolling"`, `weekLockAt: 2099`, `gameKickoffs: {…: 2099}` → allowed. **F1-c**: the member changes their pick on a game whose `status` is `final` to the known winner → allowed. Server side, `lockAndScoreWeeks` then never locks the week (`effectiveWeekLockMillis` = 2099) and scores only when every game is final, leaving the window open all Saturday.  
Related: **F6-a** a member can *create* any week doc with arbitrary fields (`weeks create: isCommissioner || isGroupMember`, no validation); **F6-b** on the selection→picking hop members may set `pickDeadline` to any value (2099).  
**Blast radius:** the core game. Undetectable in the UI (the pick doc looks normal).  
**Fix direction:** lock-snapshot keys and `pickDeadline` writable only by commissioner and Cloud Functions; compute `pickDeadline` server-side (the `selectionDeadlineJobs` path already does this). Members should not update week docs at all — replace `nominationCount` maintenance with a server aggregate (P-4) and the "slate filled → open picking" transition with a Cloud Function trigger on nominations. Add rules tests for lock-key-only writes and for member week creation.

### R-4 (P1) Nomination payloads are trusted into `games` and scoring

**Evidence:** `nominations` create requires only `submittedBy == request.auth.uid` and selection-open. `materializeNominations` (`functions/src/materialize.ts` L44–79) copies `espnEventId`, `homeTeamId`, `awayTeamId`, `spread: Math.abs(Number(n.spread ?? 0))`, `spreadTeamId`, `kickoff` into `games/{espnEventId}`. Those fields then drive: ESPN matching (`eventById.get(game.espnEventId)`), `coveredTeamId` in `scoring.ts`, and `lockSnapshotFromGames` in `pickLock.ts`. PoC **F4-a/b** allowed.  
**Concrete effects:** a bogus `espnEventId` never goes final → `allFinal` never true → the week never scores (denial of service on a league). A kickoff a day late keeps a rolling game unlocked after the real kickoff (and `revealLockedGames` never reveals it). `spread: "abc"` → `Number("abc")` is `NaN` → `adjusted` is `NaN` → `adjusted === 0` false, `adjusted > 0` false → **away team always covers**. Swapped `homeTeamId/awayTeamId` inverts results.  
**Fix direction:** materialize from ESPN, not from the nomination: keep only `espnEventId` from the client, fetch the event server-side (`slatePayloadFromEspn` in `week0Split.ts` already does exactly this) and write teams, kickoff, and spread from ESPN. Rules: `espnEventId is string && espnEventId.matches('^[0-9]+$')`, `spread is number`, `kickoff is timestamp`.

### R-5 (P1) Pick documents are unvalidated

**Evidence:** `memberPickWrite` checks only `isLocked`/`submittedAt` shape. PoC **F5-a**: `confidenceGameId` accepted in a league with `rules.allowConfidencePick == false`; the flag is enforced only in `PicksViewModel` (`group.rules.allowConfidencePick ? confidenceGameId : nil`) and never in rules or `scoring.ts` (`scorePicks` doubles the weight whenever the field is present). **F5-b**: `isLocked: true` with `submittedAt` three days in the past accepted → `applyLatePickPenalty` compares client `submittedAt` to `deadline` and waives the penalty. **F5-c**: `displayName: "commish"` accepted; the board and `revealedPicks` render it.  
**Fix direction:** rules — `submittedAt == request.time` when `isLocked == true`; `confidenceGameId == null` unless `group.rules.allowConfidencePick == true` and the id is in `week.gameIds`; drop `displayName` from pick docs (join from member doc at read time, as the server already does for `revealedPicks` consumers). Functions — ignore `confidenceGameId` when the league rule is off.

### R-6 (P1) Chat moderation can be undone by the author

**Evidence:**

```
allow update: if isSuperAdmin()
  || (isGroupMember(groupId) && resource.data.userId == request.auth.uid
      && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['text', 'editedAt', 'isDeleted']))
```

The author may set `isDeleted` in either direction, so a message hidden by the commissioner (`isDeleted: true`) or by `onReportCreated` after three reports can be un-hidden by its author. `displayName` and `avatarColorHex` are free text on create (PoC **F7-a**: a member posted as "commish"). Any member may replace the whole `reactions` map.  
**Blast radius:** App Review Guideline 1.2 (UGC moderation) and in-league harassment.  
**Fix direction:** author update rule must forbid `false ← true` on `isDeleted` (`!(resource.data.isDeleted == true && request.resource.data.isDeleted == false)`); set `displayName` server-side in `onMessageCreated` or validate against the member doc; move reactions to `reactions/{uid}` subdocs.

### R-7 (P1) Rolling-lock rules exceed Firestore's expression budget

**Evidence:** `rollingChangedUnlocked` unrolls `rollingIndexUnlocked` twenty times, each doing list/map lookups plus `hasAny`, on top of four `get()` calls per write. The emulator logs `Unable to evaluate the expression as the maximum of 1000 expressions to evaluate has been reached` and the write is denied. Measured with a legitimate member writing all picks at once:

| Rolling slate size | create pick doc | update pick doc |
|---|---|---|
| 5 | allowed | allowed |
| 10 | allowed | allowed |
| 15 | allowed | **denied** |
| 20 | **denied** | **denied** |

Member-select leagues derive slate size as `members × selectionsPerMember` (`GroupRules.expectedSlateSize`), default 3 per member, so a 5-member rolling league already sits at 15.  
**Fix direction:** stop evaluating per-game kickoffs in rules. Have `lockAndScoreWeeks` (which already runs every 5 minutes and computes `gameIsLocked`) write `lockedGameIds: [...]` onto the week, then the rule becomes one expression: `!request.resource.data.picks.diff(resource.data.picks).affectedKeys().hasAny(week.lockedGameIds)`. Or move pick submission to a callable.

### R-8 (P2) Commissioner power is unbounded and unaudited

**Evidence:** PoC **F8-a**: commissioner changed `spread`/`spreadTeamId` on a game with `status: final` (no status check in `commissionerGameUpdate`); scoring recomputes from that field (P-3). `commissionerPickWrite` allows writing any member's picks while the week is `locked` (after kickoffs, before scoring). `members update: isCommissioner(groupId) || …` has no allow-list for the commissioner, so they can set any member's `seasonWins`. `standings`, `seasons`, `career` are commissioner-writable (**F8-b**). `groups update: isCommissioner` has no field allow-list — `memberIds` can be set to include uids who never consented (they then receive pushes), and `commissionerId` can be handed to a non-member.  
**Who:** the commissioner. Leagues between friends often involve money, so "trusted role" should still be bounded and disputes should be resolvable.  
**Fix direction:** freeze `spread` once `game.kickoff <= request.time` or `status != 'scheduled'`; commissioner pick writes only for still-open games and always with `isLocked: true`; season totals and standings server-owned (R-2/P-3); log commissioner writes to an audit subcollection via an `onWrite` trigger.

### R-9 (P2) Invite-code and handle lookups are open

**Evidence:** `inviteCodes/{code}` `get: isSignedIn()` (PoC **F7-c**), and commissioner-chosen codes may be 4 characters (`InviteCodeRules`: "4–8 letters or numbers") → 36⁴ ≈ 1.7 M candidates with no rate limit; the resulting `groupId` then feeds R-1. `handles/{key}` create only checks `userId == uid` and required keys, so a user can reserve any key (PoC **F7-b**), squatting names or bulk-reserving.  
**Fix direction:** invite lookup via the join callable (rate-limited); handle create requires `handleKey == request.resource.data.displayName.lower()` (rules `string.lower()` exists) and one handle per user tracked on `users/{uid}.handleKey`.

### R-10 (P2) Client reads the rules forbid

**Evidence:** `GroupService.hydrateMemberAvatars` reads `users/{otherUid}` for every member without an avatar URL; rules allow `users` read only for the owner or admin, so every call is `permission-denied` and swallowed. Harmless, but it shows rules and client drifted and costs a denied read per member per listener fire.  
**Fix direction:** remove the read (avatars are already mirrored onto member docs on write).

### R-11 (P2) Storage: avatars public read, client-declared content type

**Evidence:** `storage.rules` — `allow read: if true`, `contentType.matches('image/.*')` (SVG passes), 2 MB cap, path bound to `{uid}.jpg`. Reasonable; tighten to `image/jpeg` and signed-in read.

### R-12 (P2) Force-update and kill switches are client-only

**Evidence:** `appConfig/live.minimumBuild` and `chatEnabled` are read by `LiveAppConfigService` / `ChatService`; nothing server-side rejects writes from a build below `minimumBuild`. Documented in `docs/WEB_ARCHITECTURE_ASSESSMENT.md` §3.  
**Fix direction:** low priority; App Check (A-1) plus a `minBuild` check in callables when they exist.

## Area 3 — Pick / standings write paths

What is right: `scoreWeek` runs in a transaction and skips already-scored weeks; `adminRescoreWeek` re-sums season totals idempotently; `materializeNominations` keys games by `espnEventId` so duplicates collapse; `revealedPicks` is function-only; `submissions` cannot carry `picks`; iOS `preservingLockedPicks` keeps locked games from being rewritten in the normal client.

### P-1 (P1) Pick locking depends on the scheduler and on `pickDeadline` existing; scoring ignores `isLocked`

**Evidence:**

```
function pickDeadlineOpen(groupId, weekId) {
  …
  let lateOk = !isRollingWeek(week) && … group.rules.allowLatePicks == true;
  return week.status == 'picking'
    && (lateOk
        || (isRollingWeek(week) && !weekFullyLocked(week))
        || (!isRollingWeek(week)
            && (!week.keys().hasAll(['pickDeadline']) || week.pickDeadline == null || request.time < week.pickDeadline)));
```

The rule is open whenever `status == 'picking'` and any of: late picks allowed, **or the week has no `pickDeadline`**, or the deadline is in the future. The only thing that closes it is `lockAndScoreWeeks` flipping `status` to `locked`, which for a first-kickoff week happens on the next 5-minute tick after `pickDeadline` — and **only if `pickDeadline` exists** (`index.ts` L406–409: `fullLockMs = deadline ? deadline.toMillis() : fullLockMs`, where the fallback is `null` for a non-rolling week with no lock snapshot). Consequences:

- Any week that reaches `picking` without a `pickDeadline` is open to **every member until it is scored** (after all games are final). Two supported paths produce that state: `adminSetWeekStatus({status: "picking"})` with no `pickDeadline` (`admin.ts` L159–216 sets status only), and the member transition `changed.hasOnly(['status', 'nominationCount'])` in `memberWeekFieldUpdate` (no deadline required). PoC **F1-baseline** is this state plus `allowLatePicks`: an edit on a final game is accepted.
- With `allowLatePicks` on a normal week the window is the ≤5 minutes between first kickoff and the scheduler tick — small, but the games in it are live.
- `scorePicks` (`scoring.ts` L159–187) **never checks `isLocked`**, so a draft written by `savePickDraft` (`isLocked: false, submittedAt: nil`) is scored in full; `applyLatePickPenalty` (L70–87) needs both `submittedAt` and `deadline`, so a never-submitted late draft pays no penalty, and a submitted one can backdate `submittedAt` (R-5, PoC F5-b).
- R-3 turns "until the tick" into "until scored" at will.

**Fix direction:** late picks must be per game — accept a pick for game G only while `G.kickoff > request.time` (same `lockedGameIds` mechanism as R-7) regardless of `allowLatePicks`; require `pickDeadline` (or lock snapshot) on any transition into `picking`, including the admin callable; `submittedAt == request.time`; score only `isLocked == true` docs or treat unlocked docs as late; compute the penalty server-side from server-stamped time.

### P-2 (P1) Week state machine is implemented twice, and the client copy is a writer

**Evidence of duplication (Swift ↔ TypeScript):**

| Concern | iOS writer | Cloud Function |
|---|---|---|
| Nominations → games | `PickService.materializeNominationsIfNeeded` | `materialize.ts` |
| selection → picking + lock snapshot | `WeekTransition.toPickingUpdates`, `PickService.openWeekWithCurrentSlate`, `GroupService.lockSlateEarly` | `selectionDeadlineJobs`, `pickLock.ts` |
| Week 0 fixed slate from ESPN (writes `games`, `status: picking`, `lockedAt`) | `GroupService.seedFixedSlateIfNeeded` | `week0Split.ts` (admin migration) |
| Week doc minting | `GroupService.ensureWeekDocumentExists` (any member) | none |
| Season close / career totals | `GroupService.closeSeason` + `SeasonCloseEngine` | `autoCloseSeasons` |
| Scoring / ranking / cover | `ScoringEngine.scorePicks`, `rankedStandings`, `SlateGame.coveredTeamId` ("keep in sync" comments) | `scoring.ts` |
| Standings doc | `closeSeason` resets `standings/current` | `scoreWeek`, `refreshLiveStandings`, `adminRescoreWeek` |

Each pair has a "keep in sync" comment. The iOS versions are not just display logic — they *write* the authoritative documents, so a modified client (or an honest client with a stale rules understanding) can put a week in a state the functions never produce (e.g. `seedFixedSlateIfNeeded` writes `lockedAt` and `status: picking` from a member device). This is also the reason R-3 exists: rules had to let members write week fields so the client could drive transitions.  
**Fix direction:** single-writer principle. Cloud Functions/callables own: week creation, status transitions, lock snapshot, games, standings, seasons, career, `nominationCount`. iOS writes only: nominations (id + `espnEventId`), picks, submissions, chat, profile, member prefs. Keep `ScoringEngine` for optimistic display only and add a contract test that feeds identical fixtures to Swift and TS and asserts equal output (both test suites already exist).

### P-3 (P1) Scoring recomputes from live `spread` fields, not from the final result

**Evidence:** `lockAndScoreWeeks` stamps `winnerTeamId = coveredTeamId(game, home, away, mode)` when a game goes final (L450), but `scorePicks` (`scoring.ts` L170–187) calls `coveredTeamId(game, …)` again from the *current* `game.spread`/`spreadTeamId`. `winnerTeamId` is never read by scoring. So a spread edited after kickoff (R-8, or a forged nomination R-4) changes who covered; `adminRescoreWeek` re-stamps `winnerTeamId` from the edited spread too.  
**Fix direction:** copy the line into `lockedSpread`/`lockedSpreadTeamId` when the game locks (or when the week leaves `picking`), score from `winnerTeamId`, and treat `spread` as display-only after kickoff.

### P-4 (P1) Non-transactional multi-document writes and client-maintained counters

**Evidence:**
- Pick doc and `submissions/{uid}` are two sequential `setData` calls (`PickService.savePickDraft` / `submitPicks`); `reconcileOwnSubmissionPickCount` exists to repair the resulting drift.
- `nominationCount` is maintained by the client with a mix of `FieldValue.increment(-1)` and full recounts (`submitNominations`, `removeNomination`, `clearSlateGamesForSelectionReopen`, `submitCommissionerGames`), and `memberWeekFieldUpdate` lets any member set it to any value. It gates "slate filled" UI.
- `refreshLiveStandings` reads members/picks/standings then writes without a transaction; `lockAndScoreWeeks` patches each game with individual `update`s; `adminRescoreWeek` uses a batch (atomic) but reads outside it.
- Both a member client and `selectionDeadlineJobs` can flip selection→picking; `onWeekStatusChange` re-materializes, guarded only by `games.empty`.
- `commissionerUnlockAllPicks` batch-writes every pick with `submittedAt: delete` — fine, but it races with members submitting.

**Fix direction:** derive `nominationCount` with a trigger on `nominations/*` writes (or `count()` aggregation on read); write pick + submission via a callable or a Firestore batch; wrap `refreshLiveStandings` in a transaction or make it idempotent from `winnerTeamId`.

### P-5 (P2) Scoring semantics worth confirming with product

- `scorePicks` ignores `isLocked` (see P-1) — an unsubmitted draft counts.
- A slate game with no pick is a loss (`missedPickIsLoss` default `true`), except Week 0 when re-summing, detected by id regex `/(^|-)W0$/i` (`isWeekZero`).
- `standings/current` ranks by **weekly** wins only (`rankEntries`); season rank is derived client-side (`StandingBoard`), and `autoCloseSeasons` ranks by `seasonWins`, then `joinedAt`, then name — three ranking definitions.
- `applyLatePickPenalty` floors wins at 0 (a late 0-win week costs nothing).
- `coveredTeamId` returns `null` (push) on exact cover; pushes are neither win nor loss, consistent across Swift/TS.

None are security bugs; each is a place where iOS and TS could disagree after an edit.

## Area 5 — Cloud Functions / support / admin pipelines

What is right: every admin callable calls `requireSuperAdmin()` first and writes an `adminAudit` row; `submitSupport` never puts the inbox address in HTML and has a honeypot, size limits, and an allow-listed redirect origin; `supportMessages` are function-only; FCM token cleanup on `messaging/registration-token-not-registered`; the report counter moves only in a transaction; `week0Split` defaults to dry run.

### F-1 (P1) `submitSupport` rate limit is spoofable and per-instance

**Evidence** (`functions/src/supportPayload.ts` L47–54, `support.ts` L130–206):

```ts
export function clientIp(req) {
  const forwarded = headerValue(req.headers, "x-forwarded-for");
  if (forwarded) { const first = forwarded.split(",")[0]?.trim(); if (first) return first; }
  return req.ip?.trim() || "unknown";
}
```

Cloud Functions v2 runs on Cloud Run, which *appends* the real client IP to any `X-Forwarded-For` the caller sends; taking element `[0]` hands the attacker the key. `SlidingWindowRateLimit` is a `Map` in process memory (`maxInstances: 4`, scale-to-zero), so the limit resets per instance and per cold start. `invoker: "public"`, `cors: true` (any origin).  
**Blast radius:** unlimited relayed mail to the private inbox through FormSubmit/Web3Forms (provider ban, inbox flood), unlimited `supportMessages` writes with spoofed `clientIp`, and — because the form is the App Store Support URL — a reputational target.  
**Fix direction:** key on `req.ip` (set by the platform from the trusted hop) or the *last* XFF element; persist the counter (Firestore doc per hashed IP with TTL) or require reCAPTCHA Enterprise / App Check on the form; restrict CORS to `https://pickems-fb.web.app` and `https://pickems-fb.firebaseapp.com`; cap daily volume.

### F-2 (P1) Scheduled jobs scan every league with no isolation

**Evidence:** `lockAndScoreWeeks` (every 5 min), `selectionDeadlineJobs` and `deadlineReminders` (every 15 min) each start with `db.collection("groups").get()` and iterate every group and its active weeks, with per-recipient `users/{uid}` + `members/{uid}` reads inside `sendToUsers`. There is no `try/catch` per group: one thrown error (a week doc with a non-number `weekNumber` is filtered, but an ESPN parse error or a malformed `kickoff` is not) aborts scoring for **every** league that tick. Reads scale with leagues × weeks × members; the README's "$5 budget cap" — if implemented as a billing kill — would stop scoring globally.  
**Fix direction:** `collectionGroup("weeks").where("status","in",[…])` with an index (one query instead of N+1); `Promise.allSettled` / per-group try-catch with `logger.error` and continue; batch member reads; make the budget an alert (F-6), not a kill.

### F-3 (P2) Admin callables trust their inputs

**Evidence:** `adminUpsertPick` writes `picks/{userId}` for any `userId` without checking `memberIds`; `adminSetWeekStatus` accepts `status: "scored"` and sets it without running `scoreWeek`, so members see "scored" with stale standings and `lockAndScoreWeeks` will skip the week forever (`status === "scored"` → skipped). `setAdminRole` see A-6.  
**Fix direction:** membership check; for `scored`, either call the scoring path or reject.

### F-4 (P2) Secrets and deploy identity

**Evidence:** `SUPPORT_WEB3FORMS_ACCESS_KEY` is `defineString` (a plain param, stored in `.env.*` and visible in the Cloud Console env list) rather than `defineSecret` (Secret Manager). `.github/workflows/firebase-deploy.yml` authenticates with a legacy `FIREBASE_TOKEN` (`firebase login:ci` refresh token — long-lived, owner-scoped, deprecated) and runs `npx -y firebase-tools@latest` unpinned in the privileged deploy job. CI deploys with `--non-interactive` will bake `SUPPORT_INBOX_EMAIL=""` (default) — masked by the `adminConfig/support` fallback, so this is a footgun rather than an outage.  
**Fix direction:** `defineSecret` for the Web3Forms key; Workload Identity Federation with a deploy-only service account; pin `firebase-tools` to a version; keep the Firestore fallback.

### F-5 (P2) Support messages retain PII indefinitely

**Evidence:** `persistSupportMessage` stores `email`, `message`, `clientIp`, `createdAt`; no TTL. The privacy policy covers the app; confirm it covers the web form.  
**Fix direction:** Firestore TTL policy on `createdAt` (e.g. 180 days); drop `clientIp` or hash it.

### F-6 (P2) No alerting on scoring failures

**Evidence:** all failure paths are `logger.error`/`warn`. Nothing notifies the operator when a week is stuck in `locked` after every game is final, when ESPN fetches fail repeatedly, or when the scheduler throws.  
**Fix direction:** Cloud Monitoring alert on function error count; a daily `adminAuditWeekIds`-style check for "locked > 24 h after last kickoff" that emails/pushes the admin.

## 6. Vibe-code smells that create real risk

- **Allow-list by subtraction.** `memberWeekFieldUpdate` removes "fields we don't care about" before `hasOnly`, which inverts the check for writes that touch only those fields (R-3). Rules should list what a role *may* write and nothing else.
- **Create without validation, update with an allow-list.** `members`, `weeks`, `nominations`, `picks` all validate `update` more tightly than `create`; delete-and-recreate defeats the allow-list (R-2).
- **Authorization in Swift, not in rules.** Invite code, `commissionerOnlyInvites`, `allowConfidencePick`, `canRemakeSelections`, "who is a member" — all enforced only by the client (R-1, R-5).
- **Denormalized identity strings.** `displayName` is copied onto picks, submissions, nominations (`submitterName`), and messages by the client and rendered as truth (R-5, R-6).
- **Client clocks in fairness logic.** `submittedAt: Date()`, `lockedAt: Timestamp(date: Date())`, `joinedAt: Date()` are all client time; rules already know how to demand `request.time` (chat does it) (P-1, R-2).
- **Two copies of the state machine** with "keep in sync" comments, both allowed to write (P-2).
- **Scoring from mutable inputs.** `winnerTeamId` is computed and then ignored (P-3); `seasonWins` accumulates on a client-creatable doc (R-2).
- **Self-healing instead of atomic.** `reconcileOwnSubmissionPickCount`, `backfillInviteCodeIndexes`, `spreadRepair`, "keep local mirror in sync" comments — each is a race someone hit and patched on the read side (P-4).
- **Unrolled loops in rules** (`rollingIndexUnlocked` × 20) to fake iteration; the budget is finite and the failure mode is a denied legitimate write (R-7).
- **Trusting proxy headers** (`x-forwarded-for[0]`) and in-memory rate limits on serverless (F-1).

## 7. Recommended fix order (for the follow-up implementer)

Ship as small PRs in this order; each has an existing test harness to extend (`firebase/tests/firestore.rules.test.js` for rules, `firebase/functions/src/*.test.ts` for functions, `PickemsTests/` for Swift). Rules changes deploy independently of the app; iOS changes ride the next TestFlight (see `docs/TESTFLIGHT.md`).

**Wave 1 — close the cheating holes with rules only (no client change needed, one deploy):**
1. **R-3**: remove `.difference(lockSnapshotKeys())`; members may update only `nominationCount` (and, temporarily, the selection→picking hop with `pickDeadline` validated against `request.time`). Add tests: lock-key-only member write denied; member week `create` restricted to `status == 'selection'`, `nominationCount == 0`, no `pickDeadline`/`lockedAt`/lock keys.
2. **R-2**: `members` create requires membership in `memberIds`, zeros, `role == 'member'`, `joinedAt == request.time`; self-delete only when not in `memberIds`. Test delete+recreate.
3. **R-5 / P-1 (rules half)**: `submittedAt == request.time` when locking; `confidenceGameId` gated on `group.rules.allowConfidencePick`; drop or validate `displayName`. Test each.
4. **R-6**: forbid author `isDeleted: true → false`. Test.
5. **R-1 (stopgap)**: `groups get` → `isGroupMember || isSuperAdmin` **only after** verifying `joinGroup` still works via the invite-code path (it needs a group `get` before membership — so this step waits for the callable in Wave 2; until then, at minimum add `bannedUserIds` and deny `isJoiningGroup` when `request.auth.uid in resource.data.bannedUserIds`).

**Wave 2 — move trust to Cloud Functions (functions + iOS):**
6. **R-1**: `joinGroup(inviteCode)` callable (validates code, `commissionerOnlyInvites`, bans; writes `memberIds` + member doc atomically); iOS `GroupService.joinGroup` calls it; then remove `isJoiningGroup()` and tighten `groups get`.
7. **R-7 + P-1 (server half)**: `lockAndScoreWeeks` writes `lockedGameIds` per week; pick rules check `hasAny(lockedGameIds)` instead of unrolled kickoff math; late picks become per-game; `scorePicks` skips unlocked docs or penalizes from server time. Add the 15/20-game emulator case as a regression test.
8. **R-4 / P-3**: materialize games from ESPN by `espnEventId` server-side; freeze `lockedSpread` at lock; score from `winnerTeamId`. Rules validate nomination field types.
9. **P-2 / P-4**: move week minting, selection→picking, Week 0 seeding, `nominationCount`, and season close behind functions/callables; remove the iOS writers (`materializeNominationsIfNeeded`, `openWeekWithCurrentSlate`, `seedFixedSlateIfNeeded`, `closeSeason` writes). Add the Swift↔TS scoring contract test.

**Wave 3 — abuse, admin, ops:**
10. **F-1**: fix `clientIp`, persist the rate limit, restrict CORS.
11. **A-6 / F-3**: admin allow-list in `setAdminRole`, Google-only + 2SV, `revokeRefreshTokens`; membership check in `adminUpsertPick`; reject `scored` in `adminSetWeekStatus`.
12. **A-1**: App Check in monitor mode, then enforce.
13. **F-2 / F-6**: per-group error isolation, collection-group query, monitoring alert.
14. **X-1**: host legal pages on Firebase Hosting, then make the repo private.

**Wave 4 — P2 hygiene:** A-2 (revoke Apple token + deletion trigger), A-3, A-4, A-5, R-8 (freeze spreads, commissioner audit), R-9, R-10, R-11, F-4 (WIF + `defineSecret` + pin), F-5 (TTL), X-2, X-3, X-4, A-7.

Notes for the implementer: keep the existing 39 rules tests green (they encode intentional behaviour such as commissioner reopen and super-admin blast radius); every rules PR should add a probe for the specific exploit it closes; Firestore rules `get()` calls are capped at 10 per request — the current pick rule already uses 4–5, so prefer denormalized fields written by functions over more `get()`s.
